## Startup instructions

### One-command startup via launcher

```powershell
.\.venv\Scripts\python.exe -m netbalance.demo --profile uniform
```

Launcher options:
- `--config <path>`: Path to JSON configuration (default: `configs/default.json`).
- `--profile {uniform,slow-server,capacity}`:
  - `uniform`: All backends 50 ms service time, capacity 4.
  - `slow-server`: Backend `s1`/`s3` 50 ms, `s2` 200 ms; capacity 4.
  - `capacity`: Backend `s1` cap 5, `s2` cap 3, `s3` cap 2; service 50 ms.

### Four-terminal manual startup fallback

Terminal 1 (Backend s1):
```powershell
.\.venv\Scripts\python.exe -m netbalance.backend --id s1 --port 9101 --service-ms 50 --capacity 4
```

Terminal 2 (Backend s2):
```powershell
.\.venv\Scripts\python.exe -m netbalance.backend --id s2 --port 9102 --service-ms 50 --capacity 4
```

Terminal 3 (Backend s3):
```powershell
.\.venv\Scripts\python.exe -m netbalance.backend --id s3 --port 9103 --service-ms 50 --capacity 4
```

Terminal 4 (NetBalance Proxy & HTTP Service):
```powershell
.\.venv\Scripts\python.exe -m netbalance.service
```

### Cleanup and Ctrl+C behavior
The launcher traps `KeyboardInterrupt` / signals and executes `terminate_all()`. It iterates through its owned child subprocesses list (`ManagedProcess`), calls `terminate()`, waits up to 3.0 seconds, and escalates to `kill()` only on unresponsive children that it spawned. Unrelated processes on the system are never inspected or terminated.

## Dashboard controls and telemetry

- **Policy switching**: Select between Round Robin (`rr`), Least Connections (`lc`), and Smooth Weighted Round Robin (`swrr`). Dispatches `POST /api/algorithm`.
- **Backend weights**: Input integer weights (1-100) for all configured backends (`s1`, `s2`, `s3`). Dispatches `POST /api/weights`.
- **Reset metrics**: Resets counters, histograms, and selector state when inflight work is zero. Dispatches `POST /api/reset`.
- **Error feedback**: Visual flash notification with honest detail for 400 (validation), 422 (schema violation), 409 (busy reset with active work), or network unavailability.
- **Telemetry display**:
  - Inflight work, active policy, config revision, metrics epoch.
  - Work accounting totals (`received`, `succeeded`, `failed`, `rejected`, `protocol_errors`).
  - Successful proxy latency summary (`mean`, `p50`, `p95`).
  - Backend server table with health badge (`healthy`, `unhealthy`, `unknown`), active reservations, assignments, successes, failures, probe streaks, and last transition timestamp.
  - Bounded recent event flow (last 20 events rendered in reverse chronological order, labeled as application state transitions, not packet captures).

## Outage and recovery demonstration evidence

Executed via `scripts/run_demo_outage.py` against live loopback TCP sockets and HTTP API on Windows (Python 3.12.10):

1. **Step 1 — Round Robin baseline**:
   - Workload: 30 requests sent at concurrency 6.
   - Result: 30 succeeded, 0 failed.
   - Assignments: `s1: 10, s2: 10, s3: 10` (perfect cyclic distribution).
   - Saved CSV: `results/demo_rr_30.csv`.

2. **Step 2 — Policy switch to SWRR and weights 5:3:2**:
   - Reconfigured via API: algorithm set to `swrr`, weights set to `{"s1": 5, "s2": 3, "s3": 2}`.
   - Telemetry reset: epoch incremented to 1.
   - Workload: 30 requests sent at concurrency 6.
   - Result: 30 succeeded, 0 failed.
   - Assignments: `s1: 15, s2: 9, s3: 6` (matches 5:3:2 ratio exactly).
   - Saved CSV: `results/demo_swrr_30.csv`.

3. **Steps 4 & 5 — 15-second workload with s2 outage at 3s and recovery at 8s**:
   - Started 15-second continuous workload at concurrency 6 under SWRR (weights 5:3:2).
   - At offset 3.01s: Terminated `s2` process.
   - Health detection: Health probe failed; after threshold (2 consecutive probe failures = 2.0s), `s2` transitioned to `unhealthy`.
   - Window failures: During the detection window (between 2.765s and 5.047s), exactly 20 requests dispatched to `s2` failed with `BACKEND_UNAVAILABLE`.
   - Outage exclusion: From offset 5.1s to 10.1s, 250 requests were sent. All 250 requests were routed exclusively to healthy backends (`s1` and `s3`), with 0 requests sent to `s2`.
   - Recovery at offset 8.01s: Restarted `s2` process on port 9102.
   - Health probe passed; after 2 consecutive probe successes (at offset ~10.15s), `s2` transitioned back to `healthy`.
   - Post-recovery routing: 78 subsequent requests were dispatched to and successfully processed by `s2`.
   - Overall run statistics:
     - Total attempts: 731
     - Succeeded: 711
     - Failed: 20 (`BACKEND_UNAVAILABLE`)
     - Final backend assignments: `s1: 419, s2: 144, s3: 168`
     - Final backend successes: `s1: 419, s2: 124, s3: 168`
     - Final backend failures: `s1: 0, s2: 20, s3: 0`
     - Throughput: 47.20 rps
     - Client latency: mean 112.68 ms, p50 108.67 ms, p95 171.25 ms
   - Saved artifacts: `results/demo_outage_recovery.csv`, `results/demo_outage_meta.json`.
